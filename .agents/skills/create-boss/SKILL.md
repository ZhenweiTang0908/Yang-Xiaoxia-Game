# 创作 Boss

这个 skill 只给方法和取舍原则，**不给配方**。它不规定 Boss 必须有快慢刀、几个阶段、召唤、远程或任何具体招式。下面出现的具体招式都只是用来说明某个原则的例子，不是要满足的清单。如果你发现自己是在“凑齐”某类招式，就停下来，回到角色本身想。

好 Boss 的来源是**一个具体的人（或兽、或神）在用身体做一件事**，招式表只是这个人的结果。

## 用户定下的质量要求（每个新 Boss 都必须满足）

这些规定的是质量标准，不是具体招式。设计文档里要逐条写明怎么满足。

1. **技能丰富多样，并且和形象一致。** 招式要比前几位更多、更花哨、更有趣，并且每一招都能体现这个角色的身份、兵器、体型和性格。花哨要从角色身上长出来（剑客的剑花、术士的法宝、野兽的扑咬），不是凭空加特效。多样指的是动作和应对方式不同，而不是同一个动作换了数值。
2. **躲避和反制本身要好玩。** 不只设计 Boss 怎么打，还要设计玩家怎么躲、怎么还手：哪一招适合踏月闪穿过，哪一招可以跳过去下劈，哪一招被升龙斩破开，哪一招给弓箭或羊灵留出机会，哪一招需要牛大侠配合。成功化解要有清楚的反馈（Boss 的失衡、踉跄、懊恼的台词或音效）。
3. **声音要充足。** 台词要够多，覆盖登场、阶段变化、各重要技能、被玩家化解、玩家受重创、低血量和败北，同一事件准备多句避免重复（参考骑士 55 句）。**攻击的每一个动作阶段都要有合适的音效**：起手、蓄力、挥动或出手、实际命中、落地或收招，连段的每一段分别配声，体型、兵器和材质要能听出来。没有声音的动作不算完成。
4. **形象和其他 Boss 统一。** 画风、线条、上色层次和细节密度要与现有 Boss 一致（对照 `builds/qa/boss-clean-sheet.png` 和 `art_source/knight_painted/`）：不要比现有 Boss 花哨很多，也不要过于简单。体型可以不同，但要放进同一个世界。
5. **动作要更流畅，关键帧要更多。** 前三位 Boss 每位只有 6 张关键帧（`assets/art/boss_frames/`），明显不够；骑士有约 72 张（`assets/art/knight_frames/`）。新 Boss 的关键帧至少要达到骑士的水平，并且在每个招式的预备、发力、出手、跟随和收招之间补足过渡帧，让网格补间只负责细小的过渡，而不是硬撑大幅度动作。设计文档要按招式列出关键帧清单。

在这些之外，你可以自由发挥，但发挥的结果同样要回到上面五条去检验。

## 0. 先读懂现在的游戏

动笔之前先读这些，不要凭记忆：

- `README.md`：主角的完整能力（三连斩、三式搓招、蓄爆、弓、翻滚与踏月闪、羊灵、牛大侠、月露葫芦）、四境连战顺序、难度模式。
- `data/bosses/*.tres`：前三位 Boss 的招式表。`scripts/actors/boss.gd`：通用 Boss 逻辑（阶段转换、事件调度、清场）。
- `scripts/actors/knight.gd`、`knight_soul.gd`、`knight_spear.gd` 和 `docs/knight-*.md`：最新、最完整的 Boss 范例，包括选招、防重复、战怒、清理和验证方式。
- `data/arenas/boss_*.tres`、`scripts/world/battle_architecture.gd`：竞技场目前是约 960 宽的平地、两侧有墙、没有平台。
- `data/voice/boss_dialogue.json`、`docs/boss-ai-voice.md`：台词与配音流程。

再看一遍 [references/exemplars.md](references/exemplars.md)，里面写了第三、第四位 Boss 为什么成功。读的是**它们为什么能成立**，不是要照抄它们的招式。

## 1. 广泛找素材（必须做，不能跳过）

打开 [references/inspiration-library.md](references/inspiration-library.md)。这是参考库，不是必选清单。

1. **至少跨四种媒介**选素材：动作游戏、格斗/MOBA、电影、古典小说或神话，还可以加武术、舞蹈、动物行为、戏曲。只看魂类游戏会做出又一个魂类 Boss。
2. 用 WebSearch / WebFetch 实际去查，不要只凭印象：攻略站和 wiki 上的招式表与帧数据、Boss 战拆解视频的文字稿或评论、GDC 演讲、影评里对武打设计的分析、武术动作讲解，原著原文里对招式的描写。搜索可以同时用中英日文。
3. 参考库之外**至少再找到两部**作品或现实来源（某种冷兵器、某位武术家、某种动物的捕猎、某个戏曲身段）。参考库是起点，不是边界。
4. 每个来源只抽取**可迁移的东西**，按下面四栏记笔记：
   - **动作**：身体怎么发力、重心怎么移动、兵器怎么走线、起手和收势长什么样。
   - **节奏**：一段攻防的拍子、停顿、假动作、出招之间的呼吸。
   - **人物**：这个角色是谁，为什么这样打，他的骄傲、执念和弱点。
   - **玩家的回答**：面对它，玩家（或电影里的对手）是怎么化解的。
5. 把笔记写进设计文档的“灵感来源”一节，标注出处链接。**不要把某个现成 Boss 整体搬过来**：一个来源最多贡献一两个点子，最好让两个不相干的来源在同一个招式里碰撞（例如一部武侠电影里的步法，加上一种猛禽的俯冲节奏）。

## 2. 先定人，再定招

用一两句话写清楚这个 Boss：

- 他是谁，在羊小侠的旅途里处在什么位置（四境之后，第五战或替换某一战）。
- 他的**核心动词**是什么：拖、缠、等、换位、借力、压迫、引诱、守、耍……一个动词就够。
- 他和前四位有什么本质不同。对照这张表，**不要重复已有的空间和问题**：

| Boss | 一句话 | 主要在问玩家什么 |
|---|---|---|
| 守灯兽 | 石兽，三招 | 教学：看懂起手就能躲 |
| 渡影刀客 | 快刀与影步 | 近身反应与位置 |
| 噬月祭主 | 祭司，十招三阶段，场地法术 | 在全场找安全区、读空间 |
| 断誓枪骑 | 马战到步战的武人 | 读身体、躲承诺式突进、处理战怒与幽军 |

然后从人推导出 2 到 4 条**设计支柱**，比如“他从不主动追，只惩罚贪刀”。之后每个招式都要能回到支柱上解释；解释不了的就删掉。

## 3. 设计招式时问自己的问题

不要从“需要几种招式类型”出发，而要对每个候选招式回答：

- **身体**：只看剪影和动作，玩家能认出这一招吗？预兆来自身体、兵器、声音和气息，而不是文字或倒计时吗？
- **承诺**：出手之后 Boss 还会不会转向、改招？读了玩家输入临时变招的 Boss 会让人觉得不公平（参考 SNK Boss 的反面例子）。
- **判定**：伤害区域和画面上的兵器、身体是否一致？有没有前摇中就伤人、或者画面打中了却没结算的情况？
- **回答**：玩家正确的回答是什么，是跳、退、翻滚穿过、贴身、换边、打断，还是等？这个回答**和其他招式的回答是否不同**？十个招式如果都只能靠翻滚解决，其实只是一个招式。
- **窗口**：躲开之后玩家有没有可以反击的空隙？空隙有多长，是否和这一招的风险相称？
- **躲得有趣吗**：只是“按翻滚等它过去”，还是有更好玩的解法？比如从刀光下钻过、踩着冲击波跳起、在收招时绕到背后、用弓打断蓄力、在完美时机踏月闪后获得一次反击。高手和新手的解法最好不同：新手能安全躲开，高手能借这一招打出更大的伤害。
- **化解之后发生什么**：Boss 被躲开、被打断或被反击时有没有专门的反应动作、音效或台词？好的反应会让玩家感到“我读懂了他”。
- **主角的能力**：这一招会让主角的哪项能力更有用，哪项变得没用？三式搓招、弓、羊灵、牛大侠、葫芦里，至少要有几样在这场战斗里有用武之地；如果要压制某个系统（例如封葫芦），要有清楚的理由和预兆，而且不能一直压。
- **2D 平地**：在横版平地上，这个动作在左右和上下两个维度上怎么展开？墙角、头顶、身后是否会形成必死的位置？
- **人物**：这一招是不是只有这个人才会用？换给别的 Boss 也说得通，说明它还不够有个性。

## 4. 节奏、变化和阶段

- 选招时要防重复（参考骑士的 `pick` / `without_chained_combos`），但也要有可以学习的规律。完全随机和完全固定都不好。
- 如果有阶段，阶段变化应该**改变问题**，而不只是放大数字：换武器、换形态、换场地、换身份，或者把前面教过的东西组合起来。也可以只有一个阶段，取决于这个人。
- 阶段转换时清掉旧攻击、给玩家重新站位的时间（现在 `boss.gd` 是 1.25 秒无伤加 0.65 秒空档），转换本身要像这个角色会做的事。
- 招数和压力是逐渐递进的：先教，再考，最后组合。参考作品里的“第一次见面”往往比最难的那一招更值得研究。
- 留出喘息：Boss 犹豫、整理、挑衅、走位的时刻，也是表现性格的机会。

## 5. 呈现与声音

- 动作美术沿用项目当前的手绘关键帧加二维网格补间（看 `docs/knight-2d-rebuild.md`、`docs/ANIMATION.md`），不要为单个 Boss 引入新的渲染技术。
- **关键帧**：先按招式列出姿态清单，每招至少覆盖预备、蓄力顶点、出手、命中瞬间、跟随、收招，大幅度的转身、跳跃、挥舞再补中间帧；另外补待机呼吸、走动或步法循环、转身、受击、被化解的失衡、阶段转换、败北。命中瞬间必须正好显示出手姿态，不能让伤害出现时武器还在身后。截图对比相邻关键帧，检查脚底、兵器端点和左右朝向是否连贯；看到跳帧、滑步或姿态“瞬移”就补帧。
- **形象一致**：新图生成或绘制前，先把现有 Boss 的图放在一起对照，提示词沿用 `art_source/knight_painted/` 的风格描述，生成后与现有 Boss 并排截图给用户确认。
- **音效**：每一招的每个动作阶段都要配声（起手、蓄力、挥动或出手、实际命中、落地或收招），连段每一段单独配声；另外配步伐、披挂或身体摩擦、喘息或发力喊声、被化解、受击和阶段转换。挥空不播命中声（看 `docs/combat-impact-audio-mini-spec.md`、`docs/scene-combat-audio.md`、`scripts/core/enemy_audio_catalog.gd`）。设计文档里列出完整的音效表，按招式和阶段对应。
- **台词**：写出人物，不要解说招式。数量参考骑士（55 句），覆盖的事件要比骑士更全，每个事件准备多句。普通台词至少间隔 12 秒，不抢牛大侠的语音（看 `docs/boss-ai-voice.md`）。
- 最新的方向（骑士）是少文字界面：没有危险矩形、感叹号和招式名，预兆全靠身体与特效。新 Boss 默认沿用这个方向；如果某招确实需要地面标记，要在设计文档里说明理由，交给用户决定。

## 6. 平衡与可调

- 生命、伤害和前摇时长先参考同位置的 Boss（祭主 3600、骑士每阶段 2400，伤害多数在 10 到 30 之间），按位置调。不能有无法躲避的固定伤害，除非用户明确要求。
- 所有关键数值（生命、各招伤害、前摇、冷却、速度、概率）都接进 F2 参数面板，不要硬编码在逻辑里。
- 从容模式（主角承伤 70%）下要能打，标准模式下要有挑战。

## 7. 交付流程

1. **设计文档先行，不写代码**：写 `docs/<boss-id>-design.md`，包括灵感来源（带链接与每个来源借了什么）、人物与支柱、招式表（编号 / 动作与命中时刻 / 伤害 / 玩家的回答与收招，格式参考 `docs/knight-arsenal-mini-spec.md`）、阶段、与主角各系统的互动、音频与台词清单、美术需求、可调参数、验证目标。
2. 把设计给用户看，**等用户确认后再实现**。如果用户只要设计方案，就停在这一步。实现规模较大时，用 `brief-to-spec` / `spec-to-plan` 拆分。
3. 实现时新 Boss 放在独立脚本里（像 `knight.gd` 那样，通过 `boss_script` 接入），数据放在 `data/bosses/` 和 `data/arenas/`，不要把逻辑塞进通用 `boss.gd`。
4. 测试遵守 `godot-headless-test` skill。至少覆盖：每招都能被选中；前摇中不造成伤害；命中范围和时间与动作一致；每段只结算一次；转阶段、死亡、玩家死亡都能清掉全部攻击和召唤物；左右朝向都正确；每个动作阶段都触发了对应音效、每个台词事件都有音频文件。再出真实渲染截图和动作预览视频让用户看流畅度，并和现有 Boss 并排截图对比画风。
5. 打包和部署遵守 `release-deploy` skill，用户没说“部署”就不部署。

## 自查：要避免的情况

- 把参考库里某个现成 Boss 换皮搬过来。
- 为了“完整”而凑招式类型，或者照抄上面任何一个例子。
- 十个招式只需要一种回答。
- 画面和判定对不上，前摇偷伤害，出手后跟踪转向。
- 全屏或必中的伤害，或者靠读取玩家按键来反制。
- 阶段变化只是数值加倍。
- 只用文字提示才能看懂的招式。
- 只查魂类游戏，或者只凭记忆不去实际搜索。
- 招式和形象对不上，或者“花哨”只是堆特效。
- 躲避只有“翻滚等它过去”一种玩法，化解后 Boss 没有任何反应。
- 有动作没有声音，或者台词少到很快开始重复。
- 画风比其他 Boss 明显华丽或明显简陋。
- 关键帧太少，靠补间硬拉大幅度动作，出现滑步、跳帧或姿态瞬移。
